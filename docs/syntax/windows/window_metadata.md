# Window Metadata Functions

This document defines the intended semantics for SQL-visible window metadata functions:

```sql
window_start()
window_end()
```

Design status: these functions are the window metadata contract for implementation. They describe
the meaning that runtime processors and planners must preserve when support is added.

## General Contract

`window_start()` and `window_end()` expose metadata for the current logical window instance that
produced an aggregate result.

- Both functions take zero arguments.
- Both functions return `TimestampValue` values: UTC timestamps stored as signed Unix epoch
  microseconds.
- Every row emitted from the same logical window emission has the same `window_start()` and
  `window_end()` values.
- The functions read metadata attached by the window processor. They must not compute time from the
  projection stage or sink stage.
- Sink-side transformations such as delta output, empty suppression, encoding, and materialization
  must not reinterpret or recompute these metadata values.

The source of the metadata depends on the window kind:

- Time windows use the window's logical time domain.
- Non-time windows use the window processor lifecycle clock for the window instance.

## Processing-Time Mode

In processing-time mode, input tuple timestamps are derived from runtime processing time. Time-window
metadata therefore also uses processing time, but it is still computed from the window's logical
boundary rather than from projection or sink delivery time.

| Window | `window_start()` | `window_end()` |
| --- | --- | --- |
| `tumblingwindow(time_unit, length)` | The fixed bucket start computed from the tuple timestamp. | The fixed bucket end: bucket start plus `length`. |
| `slidingwindow(time_unit, lookback)` | The trigger tuple timestamp minus `lookback`. | The trigger tuple timestamp. |
| `slidingwindow(time_unit, lookback, lookahead)` | The trigger tuple timestamp minus `lookback`. | The trigger tuple timestamp plus `lookahead`. |
| `countwindow(count)` | The timestamp of the first accepted tuple that opens the count window instance. | The timestamp of the `count`th accepted tuple that completes the window and triggers emission. |
| `statewindow(open_expr, emit_expr)` | The timestamp of the accepted tuple where `open_expr` opens the state window instance. | The timestamp of the accepted tuple where `emit_expr` closes and emits the state window instance. |
| `eoswindow()` | The timestamp of the first accepted tuple in the EOS window segment. | The timestamp of the last accepted tuple in the EOS window segment when end-of-stream closes and emits it. |

## Event-Time Mode

In event-time mode, input tuple timestamps are derived from the configured event-time column before
window processors see the rows. Window metadata therefore uses event time for both time windows and
non-time window lifecycle transitions.

| Window | `window_start()` | `window_end()` |
| --- | --- | --- |
| `tumblingwindow(time_unit, length)` | The fixed event-time bucket start computed from the tuple event timestamp. | The fixed event-time bucket end: bucket start plus `length`. |
| `slidingwindow(time_unit, lookback)` | The trigger tuple event timestamp minus `lookback`. | The trigger tuple event timestamp. |
| `slidingwindow(time_unit, lookback, lookahead)` | The trigger tuple event timestamp minus `lookback`. | The trigger tuple event timestamp plus `lookahead`. |
| `countwindow(count)` | The event time of the first accepted tuple that opens the count window instance. | The event time of the `count`th accepted tuple that completes the window and triggers emission. |
| `statewindow(open_expr, emit_expr)` | The event time of the accepted tuple where `open_expr` opens the state window instance. | The event time of the accepted tuple where `emit_expr` closes and emits the state window instance. |
| `eoswindow()` | The event time of the first accepted tuple in the EOS window segment. | The event time of the last accepted tuple in the EOS window segment when end-of-stream closes and emits it. |

Event-time watermarking controls when time windows may emit. It does not change the metadata
boundary values. Late-event tolerance affects whether rows are accepted and when watermarks advance;
it does not alter the boundary formula for accepted rows.

## Notes

For non-time windows, `window_start()` and `window_end()` are lifecycle metadata. The lifecycle clock
is the same clock carried by accepted tuple timestamps. In processing-time mode this is processing
time; in event-time mode this is the configured event time.

## Implementation Design

The implementation should treat window boundaries as collection-level metadata generated by window
processors. Expression evaluation should read that metadata; it should not recompute boundaries from
SQL expressions, row timestamps, projection time, or sink delivery time.

### Metadata Model

The runtime should attach typed metadata to collections:

```rust
struct WindowMetadata {
    start: TimestampValue,
    end: TimestampValue,
}

struct CollectionMetadata {
    window: Option<Arc<WindowMetadata>>,
}
```

The `Collection` trait should expose read-only metadata access. Concrete collection types such as
`RecordBatch` should store the metadata and provide constructors or helpers for copying metadata
from an input collection when they create a derived collection.

The main invariant is:

```text
A collection with window metadata represents exactly one logical window emission.
```

### Expression Evaluation

`window_start()` and `window_end()` should be represented as explicit internal scalar expressions,
not as ordinary custom functions:

```rust
enum WindowMetadataField {
    Start,
    End,
}

enum ScalarExpr {
    WindowMetadata { field: WindowMetadataField },
    // ...
}
```

Evaluation should use a row context that includes both the current tuple and the current collection
metadata:

```rust
struct EvalRowContext<'a> {
    tuple: &'a Tuple,
    collection_metadata: Option<&'a CollectionMetadata>,
}
```

`ScalarExpr::eval_with_tuple` can remain as a compatibility entry point for expressions that do not
need collection metadata. Operators that evaluate `window_start()` or `window_end()` must evaluate
with the row context so the metadata is available.

If a window metadata expression is evaluated without window metadata, evaluation should fail with a
clear internal/planner error. The planner should reject user queries that can reach this state.

### Planner Contract

The planner should recognize `window_start()` and `window_end()` as built-in window metadata
functions and lower them to `ScalarExpr::WindowMetadata`.

Planner validation should ensure:

- The functions take zero arguments.
- They are used only in a query with a supported window.
- They are not treated as aggregate functions or ordinary custom functions.
- They are evaluated only after the window processor has attached metadata.
- Fixed output layout remains planner-owned. Window metadata is a hidden input to expression
  evaluation until projected as an explicit output field.

### Metadata Generation

Window processors are responsible for generating metadata for each emitted window collection.

Time-window processors should generate metadata from the logical time boundaries:

- `tumblingwindow`: bucket start and bucket end.
- `slidingwindow`: trigger-relative start and end.

Non-time-window processors should generate metadata from processor lifecycle transitions:

- `countwindow`: timestamp of the first accepted row that opens the count window, and timestamp of
  the row that completes it.
- `statewindow`: timestamp of the `open_expr` transition row, and timestamp of the `emit_expr`
  transition row. If graceful shutdown flushes an active state window, the end timestamp is the last
  accepted row buffered in that state window.
- `eoswindow`: timestamp of the first accepted row in the segment, and timestamp of the last
  accepted row when end-of-stream closes the segment.

Both standalone window processors and fused streaming aggregation processors must generate the same
metadata for the same logical window. It is not sufficient to update only one execution path.

### Propagation Rules

Operators that create a derived collection from one input collection should copy the input metadata
to the output collection. This includes row filtering, projection, compute, ordering, layout
normalization, materialization, row-diff transformation, and source-change gating.

Collection helpers must preserve metadata for:

- `slice`
- `take`
- `apply_filter`
- `apply_projection`
- `clone_box`

Operators that merge multiple input collections into one output collection must not blindly copy one
input metadata value. They may propagate metadata only when all merged collections have equivalent
metadata. If the metadata differs, the operator must either keep the collections separate, split the
output by metadata, drop metadata only when no downstream expression can read it, or make the plan
invalid.

Source-like operators that create raw input collections should leave window metadata empty. This
includes decoding, data source reads, table scans, samplers, and event-time watermark buffering
before the window stage.

Sink-side processors should not reinterpret window metadata. In the normal physical plan, metadata
functions should already be projected into ordinary output columns before sink encoding or delivery.
Sink-side slicing for batching should still preserve metadata through the collection API, but sinks
must not depend on metadata to compute output field values.
